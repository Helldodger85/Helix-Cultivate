# Changelog

All notable changes to Helix Cultivate are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [1.5.4] - 2026-09-16

Two real control-loop bugs found via a full simulated grow cycle (all eight stages, germination through drying, plus targeted stress bursts) exercising the actual coordinator/stage-manager/climate-engine code against a live Home Assistant test instance rather than the mocked unit-test fixtures alone. Both are genuine regressions with real operational impact; neither was caught by the existing 463-test suite because each depends on a runtime condition (an uninitialized attribute's first real-world hit; a hardware state left over from a previous tick) that unit tests built around fresh, pre-seeded mocks don't naturally exercise.

### Fixed

- **A fresh dropped-VPD condition could permanently disable all climate control.** `_check_chronic_vpd_drift()` read `self._vpd_drift_since` without it ever being initialized in `HelixCoordinator.__init__`. The first time that method ran while leaf VPD was already outside the target band — a normal situation after a Home Assistant restart, a fresh install, or a stage transition into a tighter band — it raised an unhandled `AttributeError`. Because the failing branch never got the chance to assign the attribute, it re-raised on every subsequent tick too, aborting the coordinator's entire update cycle *before* `ClimateEngine.run()` ever ran — silently disabling heater/AC/humidifier/dehumidifier/exhaust control, the light schedule, and DLI/energy accumulation for as long as the excursion lasted, with no error surfaced anywhere but the log. Fixed by initializing `_vpd_drift_since`/`_chronic_drift_alert_fired` alongside the existing dew-point dwell-timer init (same class of gap as the `_appliance_unavail_since` fix from an earlier release).
- **The dew point / condensation hard override could leave Zone 1's heater and AC running at the same time.** When a sustained narrow leaf-temp-to-dew-point gap engages the override, it forces Zone 1's heater on directly and — by design (see the function's own docstring) — `run()` skips Zone 1's normal bang-bang control entirely for that tick, since that control would otherwise immediately fight the override. But Zone 1's normal control is also the only place that ever turns its AC off, and Zone 1 can perfectly legitimately have its AC already running the moment a dew point risk develops. The override never told it to stop, so it kept running alongside the heater the override had just forced on, for as long as the override stayed engaged. Fixed by having the override explicitly turn Zone 1's AC off in the same step it forces the heater on. Added a regression test (`test_sustained_override_also_turns_off_stale_ac`) covering this exact scenario.

## [1.5.2] - 2026-09-14

Two fixes: a design correction to a genuine mistake in the original v1.2.9 spec (not a Claude Code implementation error), and a real control bug in Conditioning Room's humidity handling.

### Fixed

- **The Plant Cycle tab no longer blocks stage configuration behind an active cycle.** The original v1.2.9 "No Active Cycle" empty state was specified too broadly, replacing the entire Grow Stage Timeline with the Start New Cycle form — so a grower could not view, plan, or tune any stage's targets (VPD, temperature, lighting, day-count) until a cycle was already running. The tab is now split into a compact status panel at the very top (the only part that varies by `cycle_state` — the Start form when not started, or the live Day X/Y progress and Abort Cycle when active) with the full timeline/profile editor always visible and fully editable beneath it. Stage targets tuned before Start New Cycle is pressed are exactly what that stage runs with once active — `start_cycle()` never touched persisted `stage_targets_{stage}` values, so this was purely a display/access restriction, not a data problem. Growth Mode's existing lock-while-occupied behavior (v1.5.0 Part 1) is unaffected.
- **Conditioning Room's dehumidifier (and humidifier, if mapped) was being driven by Primary Grow Space's leaf VPD**, not its own humidity — because it had no adjustable humidity target of its own at all, so nothing was ever comparing against a Conditioning-Room-specific value in the first place. Added a genuine Conditioning Room Humidity Setpoint (one flat value — Conditioning Room has no stage concept the way Primary Grow Space does) with its own slider on the Conditioning Room tab's Setpoints card, and a fixed-deadband bang-bang decision driven exclusively by Conditioning Room's own dedicated RH sensor against it. Primary Grow Space's own VPD-driven humidity control is unchanged — this is a genuinely separate decision path, not a shared or blended one.

## [1.5.1] - 2026-09-14

A small, precise correction to v1.5.0's Temporary Override section.

### Fixed

- **Light Intensity's override slider is now entirely absent — not disabled — when the Night context is selected.** The v1.5.0 spec explicitly required this control to be hidden for Night (it has no live effect there: the grow light is forced fully off outside its scheduled on-window regardless of ceiling/override), but the shipped code rendered the slider unconditionally in both contexts, with the limitation only documented rather than the control being hidden as specified. Temp Setpoint and VPD Target are unaffected — both remain fully available and meaningful in either Day or Night context.

## [1.5.0] - 2026-09-14

This release fixes a real architectural conflict: each grow stage's Profile Card previously showed its own independent, hardcoded lighting-hours value regardless of what Growth Mode (Autoflower/Photoperiod) was actually configured to — meaning the displayed schedule could directly contradict the schedule genuinely being run. It also adds two capabilities that were entirely missing: a genuinely editable per-stage day-count wired to real auto-advance timing, and a proper Day/Night-aware Temporary Override system on Primary Grow Space.

### Added

- **Growth Mode as a single, unified value.** Surfaced directly above each stage's Profile Card on the Plant Cycle tab, reading from and writing to the exact same `growth_mode` config value as Primary Grow Space's own toggle — there is no possibility of the two disagreeing. Locked read-only (with an explanation) the moment `zone2_occupied` is `True`, enforced server-side (not just disabled in the UI) so an external API call can't bypass it either; editable again the instant that flag clears, under both the dedicated-Drying-Room and no-dedicated-room topologies.
- **Every stage's lighting-hours value is now a live, read-only reflection of the real computed schedule.** The old independent per-stage `photoperiod_h` value (hardcoded per stage, e.g. Seedling 20h, completely disconnected from the actual Growth Mode computation) has been removed entirely — from the stage-target save payload, from the coded per-stage defaults, and from the one dead, never-actually-used `StageManager.current_photoperiod_h()` method that used to read it. A new single-source-of-truth method resolves this for any stage, current or not, so the Grow Stage Timeline can preview every stage's real value at once without ever risking divergence from what's actually scheduled.
- **Editable per-stage day-count**, replacing the fixed coded default, with mode-aware recommended-range guidance text beneath it (shorter ranges under Autoflower's overall shorter lifecycle, longer under Photoperiod — scoped only to that distinction, not strain-specific). This is the real value `StageManager._duration()` uses for `PROG_TIMEFRAME` auto-advance timing and the stage-progression heads-up warning's lead-time calculation, not a disconnected display number — editing and saving it genuinely changes when auto-advance fires.
- **Temporary Override system** on Primary Grow Space's Setpoints & Controls section: a Day/Night toggle plus sliders for Temp Setpoint, VPD Target, and Light Intensity, applied via a distinctly-worded "Apply Override" button (never confused with Plant Cycle's permanent "Save Stage Targets"). An override takes precedence over that context's saved stage default immediately, survives a Day/Night Smooth-Glides flip within the same stage, and clears automatically — all six slots (day/night × temp/VPD/light) at once — the moment the stage actually changes, manual or auto-advance alike. Every active override is unambiguously indicated ("🔧 Temporary override — reverts at next stage change") wherever its value is shown. The existing `number.helix_cultivate_temp_setpoint`/`vpd_target`/`light_intensity` entities now route through this same system (applied to whichever Day/Night context is actually active), rather than the old context-blind manual-override flags — which, for VPD specifically, only ever touched a display midpoint and never the real control band (`vpd_target_min`/`max`) at all. A VPD override recentres the stage's own currently-configured band width around the new value rather than fabricating an arbitrary deadband.

### Fixed

- **Saving stage targets for the currently active stage could be picked up later than the very next control tick.** `update_stage_targets` only ever wrote to the config entry's persisted options, relying entirely on the resulting entry-reload to refresh the live coordinator's in-memory config — unlike the equivalent settings-fields save path, which already patched the live coordinator directly. Verified directly (per this release's explicit instruction not to assume, given this area's history) rather than assumed correct; now both paths patch the live coordinator's config immediately, so a save for the active stage is confirmed to take effect on the very next tick regardless of reload timing.

### Known limitations in this release

- A dedicated Drying Room's own Reverse Cycle unit still doesn't get the real thermostat-mode upgrade Conditioning Room and Primary Grow Space received in earlier releases (noted previously, unrelated to this release's actual scope, still not addressed here).

> **Note (v1.5.1):** this release originally shipped the Light Intensity override slider rendering unconditionally in the Night context too, with its lack of live effect there only documented as a known limitation rather than the control being hidden as the spec required. See [1.5.1] below — it's now hidden entirely for Night, not merely disclosed.

## [1.4.1] - 2026-09-13

A targeted correction release addressing all three of v1.4.0's honestly-disclosed known limitations, plus a real safety-relevant sensor-sourcing audit of every Conditioning Room control path and a genuine day-count bug found in the new occupancy-transfer code. Conditioning Room's temperature and humidity sensors are physically positioned at Primary Grow Space's air intake — the true representation of what's actually entering the tent — so every control decision that touches Conditioning Room must be driven exclusively by those dedicated sensors, never by an actuator's own onboard reading (biased by that actuator's own motor/compressor/electronics waste heat while running).

### Fixed

- **Audited every Conditioning Room control path for sensor sourcing.** Reverse Cycle heat/cool decisions, dehumidifier control, Backup Heater's setpoint-gap evaluation, Deep Calibration's decay logging, and passive continuous logging were all confirmed to already read exclusively from dedicated zone sensors (`lung_temp`/`lung_rh`, read via `_read_sensor()`) — never an actuator's own attributes; `current_temperature` is not read anywhere in this codebase. Test coverage was added proving each of these decisions correctly ignores a deliberately-mismatched actuator attribute. One real gap was found and fixed: Cross-Zone Live Actuator Response Testing's magnitude calculation was comparing the wrong pair of readings (the source zone's own ending temperature against the dependent zone's starting temperature) — it now correctly measures how far the dependent zone's own dedicated sensor moved, on both ends.
- **Live day-count for a batch transferred to a dedicated Drying Room was frozen at its transfer-time value.** "Space Now Empty" snapshotted `actual_stage_durations()` once and never revisited it — since Primary Grow Space's single live stage tracker is immediately freed for a new cycle, nothing kept recomputing the transferred batch's day-count afterward. This affected not just a live display but the *archived harvest record itself*: `harvest_complete_drying_batch()` was passing that same frozen snapshot straight into the permanent record. The transfer now additionally captures the Drying stage's own true start date (never touching `stage_start_date` itself, and never resetting it to the moment the button was pressed), and both the live dashboard and the final archived record recompute the real elapsed days from that unchanging reference point — the same `date.today() - stage_start_date` pattern every other stage already uses.

### Added

- **`midea_ac.follow_me` wiring for a Reverse Cycle unit's onboard regulation.** Whenever a thermostat-capable Reverse Cycle unit's target temperature is set, its zone's dedicated sensor reading is also fed to the unit via `midea_ac.follow_me` (ESPHome's `platform: midea` climate component), so the unit's own internal control loop works from accurate ambient data instead of its own biased onboard sensor — re-sent only on a meaningful change. This is independent of, not a replacement for, never reading that entity's own `current_temperature` for Helix Cultivate's own decisions — both apply together. Best-effort and silently quiet on failure, since most installs won't have this exact hardware; **not independently verifiable against this specific device's actual ESPHome YAML from here** — if your Midea-compatible unit needs an additional IR transmitter component alongside UART for `follow_me` to take effect, that's a configuration step on the ESPHome side this release can't confirm for you.
- **Live Actuator Response Testing now runs autonomously.** It previously only ran when manually triggered from the Settings tab — the coordinator's own tick now decides on its own when a test is due per zone/actuator (a few times a day while still in the Learning phase, roughly daily once Active), the same "just happens in the background" philosophy passive logging already used. A thermostat-controlled zone's nudge-and-measure cycle now runs fully automatically: the setpoint nudge is applied and reverted by the normal control tick, and the test finishes as soon as the zone's dedicated sensor reaches the nudged target (or a safety timeout elapses) rather than always waiting out the full window. Manual triggering from the Settings tab remains available alongside this.
- **The confidence model is now a genuine multi-variable fitted regression**, not bucketed averaging. Using the same inputs already being logged (outdoor conditions, time-of-day, season, light on/off state and brightness, an approximate occupied-hours flag), an ordinary least-squares regression (numpy only — no heavier ML framework) is refit every time new data lands, on the same rolling cadence as before. This lets the model produce a sensible prediction for a genuinely novel combination of conditions by combining the separately-learned effect of each variable, rather than requiring that exact combination to have been observed before. Confidence now comes from the fitted model's own prediction-interval width (narrow = well-supported = high confidence; wide = uncertain = low confidence) instead of a raw sample count, and an early or degenerate fit (too little data, or a singular/rank-deficient design) is treated as zero confidence — deferring entirely to the safe generic fallback rather than trusting an unreliable early fit. Hourly log rows from before this upgrade lack the fields the regression needs and are simply skipped, not fabricated — a model naturally starts building confidence from zero new data after upgrading.

### Known limitations in this release

- The upgraded regression's `get_confidence_blended_bias()`/`predictive_preheat_adjustment()` outputs remain, as in v1.4.0, not yet wired into any live setpoint decision — the model fits and predicts correctly (see test coverage), but nothing in the actual control loop consults it yet. This was discovered during this release's own investigation, not introduced by it; wiring predictive learning into live control is a larger, separate decision this release doesn't make on its own.
- `predictive_preheat_adjustment()`'s own "lights-off response" bucket intentionally remains a simple running mean, not part of the new multi-variable regression — it's a single-condition measurement a multi-variable fit wouldn't meaningfully improve.
- Extending real thermostat-mode (`heat_cool`/`auto` + `set_temperature`) support to a dedicated Drying Room's own Reverse Cycle unit — currently Drying always uses discrete heat/cool/off switching regardless of the unit's own reported capabilities, unlike Conditioning Room and Primary Grow Space — was found during this release's audit but is out of scope for a targeted correction release.

## [1.4.0] - 2026-09-13

This is the largest release to date: it closes out six smaller UI bugs from v1.3.0, fixes a real day-count regression that has been silently affecting every existing install since v1.7's migration, corrects a genuine safety gap in how Conditioning Room's future calibration testing would have been gated, and introduces two substantial new capabilities — real Reverse Cycle AirCon control and an opt-in Environmental Learning System. As with v1.3.0, several of this release's premises turned out to not quite match the actual codebase once investigated (a partially-built Reverse Cycle control path already existed; Deep Calibration didn't exist yet at all) — each is called out below rather than glossed over.

### Added

- **Zone occupancy, decoupled from cycle tracking.** Primary Grow Space and (when a dedicated Drying Room is configured) the Drying Room now each carry their own real occupancy flag — "is there currently plant material physically here" — entirely separate from `cycle_state`. A new **Harvest — Space Now Empty** action (visible only when a dedicated Drying Room exists) atomically transfers occupancy from Primary Grow Space to Drying Room without touching the batch's stage tracking, cycle_id, or accumulated data — it's a transfer, not a reset. Without a dedicated Drying Room, Primary Grow Space's occupancy has no path to `False` during Drying at all, since material never physically leaves the tent in that topology — this is what actually closes off the scenario Part 3's correction below exists to prevent.
- **Harvest Complete, as its own independent action.** A dedicated Drying Room's batch can now be closed out (yield entry, real $/gram, archiving) at any time after "Space Now Empty" was pressed for it — entirely independent of whatever Primary Grow Space is doing by then, including a fresh, different cycle already germinating there. Two `cycle_id`s can genuinely coexist. The yield form accepts either grams or ounces and converts to one canonical stored unit internally.
- **Explicit, confirmed cross-zone dependency flags.** Whether Primary Grow Space (and, with a dedicated room, the Drying Room) depends on Conditioning Room for its own baseline climate is now a real, visible, always-explicit toggle in each zone's hardware-mapping form — defaulting to the conservative "depends on Conditioning Room" whenever unset, since guessing wrong here risks a ruined harvest.
- **Real thermostat-mode control for a Reverse Cycle AirCon unit.** When an AirCon entity actually reports supporting `heat_cool`/`auto` in its own `hvac_modes`, it's now driven via `climate.set_hvac_mode` + `climate.set_temperature` — letting the unit's own onboard thermostat regulate continuously — instead of HA flipping it between discrete heat/cool/off. Entities that don't report support fall back unchanged to the existing discrete switching. "AC / Cooler" is renamed to "AirCon" throughout the hardware-mapping forms to reflect this.
- **A sustained-dwell trigger for the Backup Heater**, reusing the same dwell-timer pattern already used for VPD-assist saturation detection — it now only stages on after the primary heat source has been continuously falling behind setpoint for several minutes, not on the very first tick that looks insufficient. The existing outdoor-temperature confirming floor is unchanged.
- **Primary Grow Space's hardware-mapping form reordered**: Exhaust Fan now sits under its own heading directly above the Circulation Fan Mapping section; Grow Light and DLI/PAR Sensor moved into the Fixture Type section. Pure layout — no mappings were reset by this change.
- **Environmental Learning System** (opt-in, off by default): correlates external conditions, time-of-day, lighting, and an approximate occupied-hours schedule against actuator behavior. A Learning phase (fixed, configurable duration, default 18 days) graduates unconditionally to Active — never gated on having observed any particular event — after which the model keeps refitting indefinitely. Its influence on any future predictive feedforward is always confidence-weighted (more observations for a condition means more influence for that condition; a rarely-seen condition stays mostly on the generic default), never a hard replacement. Includes Deep Calibration (cuts a zone's actuator control for a bounded window to measure free thermal decay — gated by the same occupancy/dependency rules as Conditioning Room's calibration eligibility) and Live Actuator Response Testing (available regardless of occupancy), both durably persisted so a restart never leaves an actuator stuck deliberately disabled. Storage is self-contained (the same lightweight `Store`-based persistence used elsewhere in this integration — no external database required), with an optional, off-by-default, best-effort InfluxDB/VictoriaMetrics line-protocol export for anyone who wants to build their own Grafana dashboards on top.
- New **Environmental Learning** Settings tab, with the master toggle at the top and per-zone testing controls below it — entirely absent (not greyed out) when the toggle is off.

### Fixed

- **The Harvest ROI banner has been removed from the live dashboard.** It projected a dollar figure ahead of harvest, directly contradicting an earlier, explicit decision that yield-based figures shouldn't be shown before actual grams are known. The separate, correct calculation of real $/gram at harvest close-out from actual recorded weight is unchanged.
- **The Sensor Dropout badge could appear with nothing genuine behind it.** Its visibility was driven by a raw dropout boolean that's also true when no primary sensor is mapped at all (a configuration gap, not a real hardware dropout) — clicking it then opened a popover with no real detail. The badge now only appears when there's an actual, specifically-identifiable dropped entity, matching what the popover can show. It also now escalates to red for an actuator dropout (heater, AirCon, or exhaust fan gone unavailable) versus amber for a sensor — losing control of hardware is more urgent than losing a reading.
- **The Zone Telemetry sparkline's selected timeframe reset to Live on every coordinator data push.** The parent tab was rebuilding its entire DOM (including the sparkline's own custom element) on every push, which silently recreated the sparkline with fresh default state. The parent now persists each card's selection itself and restores it after every rebuild.
- **The sparkline graph rendered at roughly a third of its card's actual width.** It was built with a fixed pixel `width` attribute rather than genuinely filling its container — it now stretches to the card's real measured width via a responsive SVG viewBox.
- **The Breeze fan-speed slider was disabled while Breeze was active**, even though Breeze varies speed *around* a base value that still needs to stay adjustable. It's now always live, labeled "(base)" while Breeze is on. The variance slider's step changed from 1% to 5%, matching the backing number entities.
- **Manually setting a circulation fan's speed reverted the moment any other settings change was saved elsewhere in the panel.** `set_fan_speed()` never persisted its writes — an in-memory-only coordinator attribute — so any unrelated settings save that triggered a config-entry reload (rebuilding the coordinator from scratch) silently discarded it back to the coded default. It's now persisted the same way Breeze's per-tier state was fixed last release.
- **`stage_start_date` has been silently frozen since the v1.7 migration.** That migration set `cycle_state` to `"active"` for every already-existing install but never actually wrote `stage_start_date` into persisted options, despite its own comment claiming day-count was preserved — so every reload since has re-derived "0 elapsed days" instead of the real count. A new migration sets today as the new stable reference point (the true original date can't be recovered retroactively) so day-counting works correctly going forward.
- **Conditioning Room's Deep Calibration eligibility was designed around the wrong occupancy.** An earlier design gated it on Conditioning Room's own occupancy — but Conditioning Room never has plants, so that check was always trivially true and missed the actual risk: destabilizing a dependent grow space's (or dependent Drying Room's) climate mid-cycle. It's now gated on every zone that's explicitly flagged as depending on Conditioning Room being simultaneously unoccupied, re-evaluated fresh every time rather than cached. (Deep Calibration itself didn't exist as a runnable feature before this release — this correction was built as the gating rule Environmental Learning's version of it now uses.)

### Changed

- The Abort Cycle button's visibility (gated on `cycle_state === 'active'`) was re-verified against this release's corrected occupancy model — no separate bug found; its existing early-return-based gating was already correct.
- `close_out_harvest()`'s record-building and archiving logic was extracted into a shared internal helper, now also used by the new dedicated-Drying-Room Harvest Complete path, so both stay consistent rather than duplicating the same accounting logic.

### Known limitations in this release

- Live Actuator Response Testing's actual step-through-increments / setpoint-nudge-and-time mechanics are scaffolded (test lifecycle, durability, cross-zone lag/magnitude tracking) but the moment-to-moment stepping/nudging action is triggered manually from the Settings tab rather than fully autonomous end-to-end — a reasonable first version given the scope of everything else in this release, not a finished production test harness.
- The confidence-weighted regression is a straightforward running-mean-per-condition-bucket model, not a fitted statistical regression — an honest, working starting point rather than a claim of higher precision than that approach can actually provide.
- A dedicated-Drying-Room batch's stage-duration data is snapshotted at the moment "Space Now Empty" is pressed, not tracked live afterward — Primary Grow Space's stage machine is freed immediately for a new cycle, and there isn't yet a second, fully independent stage tracker running concurrently for the transferred batch.

## [1.3.0] - 2026-09-13

This release closes out a safety-relevant persistence bug on the Safety Interlocks tab, fixes a canopy dashboard layout bug where disabling a sensor tier visually displaced a different tier's readings, and builds out real multi-fan-per-tier circulation mapping and genuine Breeze cycling — both of which turned out to be considerably further along in the backend than expected, once actually audited, with the real gaps sitting almost entirely in the frontend's wiring to them.

### Added

- **Live number entities for every Safety Interlocks slider.** High/low temperature cutoffs, high/low humidity cutoffs, and the sensor dropout timeout are now backed by real HA number entities (`number.helix_cultivate_safety_high_temp`, `..._safety_low_temp`, `..._safety_high_rh`, `..._safety_low_rh`, `..._sensor_dropout_min`), built with the same pattern already used for the working Heater Cutoff and Thermal Runaway controls. Dragging any of these sliders now calls `number.set_value` on a real entity that persists via the config entry, instead of only updating the on-screen label. This was audited as a full pass over every slider on the Safety tab (not just the four/five originally named) — the Dew Point Margin slider was already correctly wired from a previous session and needed no change.
- **Circulation Fan Mapping section in the gear-icon hardware form.** Each canopy tier (Upper/Mid/Lower) now has a Fan Count selector (0-4) that dynamically reveals that many fan-entity pickers. Reducing the count hides slots without clearing their selections — increasing it again brings the previous picks straight back, so nothing is lost mid-edit. This writes to the same `upper_fans`/`mid_fans`/`lower_fans` list-valued config keys the backend circulation logic (`_get_tier_fans`/`_apply_fan_speed_to_tier`) already drove every entity in — that logic already supported multiple fans per tier; it simply had no way to be configured from the dashboard panel itself (only from Home Assistant's native Options Flow wizard).
- **`CHANGELOG.md`** (this file).

### Fixed

- **Safety Interlocks sliders did not persist at all.** No slider on the Safety tab had an event listener wired to anything beyond updating its own displayed value — dragging one and reloading the page always showed the coded default again. Fixed by wiring each to its new live number entity (see Added).
- **A deeper, previously-undetected reason the fix above wouldn't have been visible even once the sliders called `number.set_value`:** the dashboard reads its displayed values for these fields from the diagnostic `exhaust_speed` sensor's attributes, not from the entity states directly — and none of the five Safety fields were exposed there. Without this, a slider would have persisted correctly under the hood but still appeared to reset to default on every reload. Now exposed alongside the existing Dew Point Margin / v1.2.8 settings attributes.
- **The actual, deepest root cause of "sliders/toggles that visually work but never take effect":** `HelixNumber` and `HelixSwitch` never pinned their own `entity_id`, unlike `HelixSensor` and `HelixSelect` (fixed in earlier releases for the identical reason). Home Assistant instead derived `entity_id` from each entity's display `name`, which for most of them does not slugify back to its stable key (`number.helix_cultivate_temperature_setpoint` vs. the `temp_setpoint` key the frontend actually calls `number.set_value` on, for example). This meant most of the panel's live sliders and toggles — temperature/VPD/light setpoints, per-tier fan speed and breeze variance, and the three Breeze switches — were silently targeting entities that didn't exist. Both entity classes now pin `entity_id` directly, and a new config-entry migration (v1.7 → v1.8) renames any already-installed entity to match, exactly as the earlier sensor/select migrations did.
- **Sensor dropout timeout was never actually configurable.** `_check_sensor_dropout()` used the hardcoded default constant instead of reading the persisted `sensor_dropout_min` config value, so changing it (via the Options Flow or the new live number entity) had no effect on the actual detection logic, even though the value itself was being saved correctly.
- **Canopy tier cards shifted position when a sensor tier was disabled.** Disabling the Mid canopy sensor collapsed its grid cell instead of leaving it empty, so Lower visually slid into Mid's column — for both temperature and humidity readouts. Fixed by rendering an explicit placeholder cell for a disabled tier instead of an empty string, so Upper/Mid/Lower always occupy fixed grid columns regardless of which are enabled.
- **Circulation Fan Matrix card showed a hardcoded "0/4 fans"** regardless of how many fans were actually mapped to a tier. The count now reflects the real number of configured fan entities, and a tier with zero mapped fans has its entire card omitted from the matrix rather than shown with a meaningless zero (distinct from the sensor-cell placeholder fix above — there's nothing to display a placeholder *for* when a tier has no fan control surface at all).
- **Fan speed sliders allowed any 1% increment** despite the underlying Template Fan wrappers only supporting 11 discrete power levels (0/10/20/.../100). Both the dashboard slider and the backing number entities now step by 10.
- **Breeze mode did not persist and could not be independently enabled per tier.** Two compounding bugs: the Breeze switches only ever updated an in-memory coordinator attribute with no call to persist it, so the "true" state was lost on any reload; and all three tiers' enabled state was read from the same single shared config key at startup, so enabling Breeze on one tier silently enabled it on all three. Both are now genuinely per-tier and persisted.
